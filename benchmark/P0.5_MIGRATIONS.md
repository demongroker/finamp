# JellyAmp P0.5 step 10 — Safe, versioned, transactional, recoverable migrations

Status: DONE (commit to land on `features/jellyamp-1.1`).
Scope: P0.5 "Implement safe data/download migrations." This change does NOT alter
what any existing migration does — it wraps the existing 7 P0.4 settings
migrations in a versioned, ordered, idempotent, failure-safe runner, and adds a
headless fixture test against a synthetic previous-version (1.0) install.

---

## 1. What the migration system looked like before (audit)

File: `lib/bootstrap/migrations.dart` (P0.4, extracted verbatim from `main.dart`).

- **Trigger**: `bootstrap()` calls `runMigrations()` once, right after `setupHive()`
  (`lib/bootstrap/bootstrap.dart:128`).
- **Not versioned**: `runMigrations()` blindly ran all 7 `_migrate*` helpers in
  order on every single launch. Each helper relied on its own internal guard
  (e.g. `downloadLocations.isNotEmpty`, `useFixedSizeGridTiles == null`,
  `deviceId == "unset"`, `featureChipsConfiguration.migrated`,
  `hasCompletedThemeModeLocaleMigration`) to be a no-op once applied. There was
  no persisted record of "how far migration got", so there was no way to know
  whether a step had already applied, and no forward path for adding a step
  conditionally per install.
- **Not transactional / not recoverable**: each helper does a single Hive `put`
  at its end (atomically per box), but there was no cross-step transaction and,
  critically, **nothing persisted progress**. If the process died or a helper
  threw between steps, the next launch re-ran everything. Because the helpers
  are guarded/idempotent this was *usually* safe, but:
  - a thrown error in any helper propagated up through `bootstrap()` and hit the
    fatal `FinampErrorApp` path (good — no silent half-migrated *continue*), but
  - there was no durable checkpoint, no per-step logging, and no test that a
    partial/failed run left the store in a recoverable state.
- **Mid-migration failure behavior**: a throw aborted startup (FinampErrorApp).
  Nothing was written back, so the next launch re-ran the whole batch. This is
  safe because the helpers are idempotent, but it was unverifiable and untested,
  and could not express "skip only the already-finished steps".

Audit gaps addressed here: versioning, per-step checkpointing, explicit
failure semantics, and an automated fixture test. The 7 migration bodies are
unchanged.

## 2. Versioning model (added)

`lib/bootstrap/migrations.dart` now defines:

- `const int currentDataVersion = 7;` — the highest migration version for the
  current release.
- A `MigrationStep { int targetVersion; String name; Future<void> Function() migrate; }`
  model.
- `_migrationSteps` — an APPEND-ONLY ordered list. The seven P0.4 settings
  migrations map to versions **1..7 in their original order**:

  | version | step              | body source               |
  |--------:|-------------------|---------------------------|
  | 1       | downloadLocations | `_migrateDownloadLocations` (unchanged) |
  | 2       | sortOptions       | `_migrateSortOptions` (unchanged) |
  | 3       | gridSize          | `_migrateGridSize` (unchanged) |
  | 4       | homescreen        | `_migrateHomescreen` (unchanged) |
  | 5       | featureChips      | `_migrateFeatureChips` (unchanged) |
  | 6       | deviceId          | `_migrateDeviceId` (unchanged) |
  | 7       | themeModeLocale   | `_migrateThemeModeLocale` (unchanged) |

  Collectively versions 1..7 are the JellyAmp 1.0 → 1.1 data migration batch
  ("version 1 = the 7 existing ones in order"). Each step advancing the version
  by one is a deliberate choice that gives per-step recovery: a crash after step
  3 resumes at step 4, not back at step 1. **Future migrations append a new step
  (version 8, 9, …) and bump `currentDataVersion`; never reorder or edit an
  existing step.**

- **Persistence**: a small Hive box `MigrationVersion` (key `version`, int)
  records the highest fully-applied step. Written only after a step completes.

### Backward compatibility for real 1.0 installs

A genuine 1.0 install has **no** `MigrationVersion` box yet, so `runMigrations`
reads `0` and runs all 7 steps exactly once. Every helper's internal guard makes
the run a no-op if the setting was already migrated, so the first launch after
this update produces the same resulting settings as before (no double-apply, no
data loss), then checkpoints version 7. A fresh install (empty settings box,
created by `setupHive`) also runs the batch; the guards short-circuit and it
checkpoints 7.

## 3. Transactional / recoverable behavior (added)

The runner in `runMigrations()`:

```dart
var storedVersion = await _readStoredVersion();
if (storedVersion >= currentDataVersion) { /* nothing to do */ return; }
for (final step in _migrationSteps) {
  if (step.targetVersion <= storedVersion) continue;
  await step.migrate();                       // try
  storedVersion = step.targetVersion;
  await _writeStoredVersion(storedVersion);   // checkpoint AFTER success
}
```

Guarantees:

- **Ordered**: steps run in `_migrationSteps` order; already-applied steps
  (`targetVersion <= storedVersion`) are skipped.
- **Idempotent**: the version gate makes the batch run at most once; additionally
  every step retains its original guard, so even a re-run after a partial
  failure cannot double-apply or corrupt.
- **Recoverable**: the version is persisted only *after* a step fully applies
  (each step ends in a single atomic Hive `put`). A crash mid-batch leaves the
  store at the last completed step; the next launch resumes there.
- **Failure-safe / no silent half-migrated state**: if any step throws, the
  error is logged and **rethrown**. The caller (`bootstrap()`) already maps a
  startup failure to the fatal `FinampErrorApp` — the app does NOT proceed as if
  migration succeeded, and no user download/library state is destroyed. On the
  next launch, only the failed step (and later steps) re-run, safely.
- **No weakening of the existing failure path**: P0.4's fatal-error surface is
  preserved exactly; we only make the *granularity* of retry finer (per-step
  instead of whole-batch) and make it observable.

> Hive has no cross-box transaction, so each step is transactional per box (a
> single `put` per step). The design therefore emphasizes *recoverability* —
> the standard way to make non-transactional stores safe — rather than
> pretending to multi-box atomicity.

## 4. Fixture test — `benchmark/migration_bench_test.dart`

Headless REAL-Isar test (pattern from `db_bench_test.dart`: loads `libisar.so`
via `Isar.initializeIsarCore`, opens `DownloadItemSchema` on a temp dir). Usage:

```bash
flutter test benchmark/migration_bench_test.dart
```

It builds a **synthetic 1.0 install** and runs the real `runMigrations()`:

Fixtures built:
- **Hive `FinampSettings`** box: legacy `downloadLocations` list (no map yet),
  legacy `sortBy`/`sortOrder` (no per-tab maps), legacy `useFixedSizeGridTiles`,
  legacy cluttered home layout (`DefaultSettings.homeScreenConfigurationLegacyCluttered`),
  unmigrated feature chips, `deviceId == "unset"`, `hasCompletedThemeModeLocaleMigration
  == false`, mutable `showTabs`/`tabOrder` without home.
- **Legacy Hive `ThemeMode` / `Locale`** boxes with real 1.0 values.
- **Isar `DownloadItem`** rows representing explicit downloads:
  - an explicit **track** (state `complete`, `path` set, ownership marker
    `userTranscodingProfile` set),
  - an explicitly downloaded **artwork image** (state `complete`, marker set),
  - a **library-filter `finampCollection`** row (P0.1 discriminator),
  - a **paused** download (P0.2 appended enum state).

Assertions (all pass):
- **No data loss**: every legacy settings value is migrated in place
  (downloadLocations → map keyed by generated UUID; sort → per-tab maps; fixed
  grid size → `gridImageSize`; home + artist tabs added; feature chips
  `migrated`; device id generated; theme + locale pulled from legacy boxes and
  the boxes deleted; `hasCompletedThemeModeLocaleMigration` set). All 4 Isar
  rows survive (`count == 4`).
- **Downloads recognized / playable / protected**: explicit track keeps
  `state == complete`, `path`, and `userTranscodingProfile != null` — the exact
  ownership marker `isExplicitUserDownload()` checks first and that cache cleanup
  consults, so the download stays recognized, indexed, playable and protected
  from cache cleanup.
- **New schema readable post-migration**: the library-filter row is found via
  the indexed `finampCollectionLibraryIdEqualTo('lib0')` bounded query and reads
  back `finampCollectionLibraryId == 'lib0'`; the paused row round-trips
  `DownloadItemState.paused` and `DownloadItemState.paused.index == 8` (appended
  ordinal).
- **Idempotency**: re-running `runMigrations()` is a no-op — version stays at
  `currentDataVersion`, no double-apply, no download row lost.

## 5. P0.2 schema migration-safety check (finampCollectionLibraryId + paused)

Both P0.2 schema changes are **additive and safe on existing 1.0 installs**, and
the fixture test now proves the read paths:

- `DownloadItem.finampCollectionLibraryId` (`finamp_models.dart:1659`) is a
  **nullable, non-unique, additive `@Index()`** field. Adding it causes Isar to
  build the index in place from existing rows — no schema-version bump, no
  collection drop, no 1.0 data loss (documented in the field comment and the
  P0.1 notes; see `references/isar-query-optimization.md`). Existing rows that
  predate it read back `null` and are backfilled by the session-guarded
  `_backfillFinampCollectionLibraryIds` in `downloads_service.dart`. The test
  confirms the index is queryable on a DB opened with the current schema.
- `DownloadItemState.paused` is **APPENDED at the end of the enum**
  (`finamp_models.dart:1824`), ordinal 8. Isar stores enums by ordinal, so all
  pre-existing rows (ordinals 0–7) are unaffected. The test confirms a `paused`
  row round-trips and that the enum value is ordinal 8.

Because these are additive (index rebuild in place + appended enum ordinal),
opening an existing 1.0 Isar DB with the current schema is a no-op migration
that preserves every row — exactly what the fixture test verifies.
