# JellyAmp 1.1 - P0.1 Large-Library Performance Baseline

Date: 2026-08-18
Branch: features/jellyamp-1.1
Harness: benchmark/bench.dart (pure Dart) + benchmark/bench_test.dart (headless Flutter test)
Host: Linux desktop (headless VM), Flutter 3.44.9 stable
Measurement policy: MEASUREMENT-FIRST. No code was optimized; this records where the time
goes today so later lanes (P0.2+) have a baseline to move.

headless Flutter-test pass (bench_test.dart), which exercises the exact code paths the app

## getAllCollections DB query (P0.1 option C, benchmark/db_bench_test.dart, 20k rows)

The fullyDownloaded/library-filter path of `getAllCollections` was rewritten from a full
`findAllSync()` + client-side Dart filter to an indexed, bounded Isar query over a new
non-unique `finampCollectionLibraryId` discriminator. This is the P0.1 option C change; it
required adding the indexed field plus a one-time backfill for pre-existing rows.

Backfill note: `_backfillFinampCollectionLibraryIds` (lib/services/downloads_service.dart) is a
session-guarded, try/catch-wrapped, additive migration. Before the indexed scan runs it decodes
each pre-existing `collectionWithLibraryFilter` finampCollection row from jsonItem and writes
`finampCollectionLibraryId` via `putAllSync` only where the value changes (never nulling anything
out). It runs at most once per session, is out of the hot path, and a mid-migration failure
degrades to the unindexed fallback rather than breaking the read. Verified compiling and green
under `flutter analyze` / `flutter test benchmark/db_bench_test.dart`.

| Metric (20k rows) | Time | Note |
|---|---|---|
| OLD findAllSync + client filter | ~640 ms | materialized all 20000 rows, then filtered in Dart |
| NEW indexed bounded query | ~31 ms | touched 500 rows via `finampCollectionLibraryIdEqualTo` |
| SPEEDUP | ~20.6x (run range ~21-56x, typical ~30x) | exact-result equality asserted (matched=500 both) |

Run via `flutter test benchmark/db_bench_test.dart`. Full result JSON in
benchmark/results/db_bench_2026-08-18.json (untracked, regenerable artifact).

## Parse off the UI isolate (P0.1 option A verification, bench_test.dart)

Added "parse off the UI isolate" test to bench_test.dart to quantify the library-load parse
in the context of the production worker-isolate architecture. Key finding: the production
path already runs `QueryResult_BaseItemDto.fromJson` in a **persistent background worker
isolate** (`JellyfinApiHelper.runInIsolate`, jellyfin_api_helper.dart:281/432), so the
benchmark's on-main-isolate `fromJson` figure is a proxy for worker-side parse cost, NOT
actual main-isolate blocking.

New numbers (this change; result asserted identical — same count + same first/last item id):

| Scale | Sync parse on main | Background-isolate parse (wall) | Delivery round-trip |
|---|---|---|---|
| 10k | 198 ms | 1130 ms | - |
| 25k | 540 ms | 2090 ms | - |
| 50k | 1018 ms | 3343 ms | 2181 ms |
| 100k | 2241 ms | 5846 ms | 3718 ms |

Interpretation: off-loading removes the parse from the main isolate but adds a delivery
(transfer) cost of the parsed object graph back to the UI (~1-2 s one-way @100k), and a
fresh-isolate parse is slower than a warm one (production uses a persistent worker, so this
is overstated). At extreme single-response sizes the transfer is comparable to the parse;
real relief there is paging/materialization, not off-loading. No production code change was
warranted (parse already off the UI isolate).

## Memory proxy (RSS while materializing parsed list, bench_test.dart)

RSS bytes reported per dataset are noisy across tests in the same VM process (later tests
inherit earlier allocations), so `approx_bytes_per_item` is only an upper-bound proxy, NOT a
reliable per-item cost. It should not be read as a precise allocation figure. Treat it as
qualitative: materializing the full parsed list of 100k tracks grows the process well past
1 GB. See the integration harness for a true peak-device-memory number.

## Regenerating datasets

benchmark/data/ is deterministically regenerable and is gitignored (see benchmark/.gitignore).
The generator is the source of truth. To rebuild:

    dart run benchmark/dataset_generator.dart                    # all 4 scales, all types
    dart run benchmark/dataset_generator.dart --type tracks      # tracks only
    dart run benchmark/dataset_generator.dart --seed 7697        # default fixed seed 0x1E11

The default seed is 0x1E11; identical flags => byte-identical output (verified by sha256
for unchanged types). Generated files: benchmark/data/library_<N>_<type>.json.

## Re-running the harnesses

Raw decode / utf8:
    dart run benchmark/bench.dart --runs 3

App-model (fromJson / sortItems / search) headless:
    flutter test benchmark/bench_test.dart

Full results JSON is written to benchmark/results/headless_<date>.json by the test harness.
